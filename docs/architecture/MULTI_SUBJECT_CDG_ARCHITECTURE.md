# Multi-Subject CDG Architecture (Phase 11 — additive, approved-in-principle)

## 1. Subject identity
`EntityBase.subject: Optional[str]` (versioned attribute, not encoded in IDs)
already supports Mathematics/Physics/Chemistry. Subject entities
(`EntityType.SUBJECT`) exist; the Mathematics graph currently has none —
backward compatible to add them.

## 2. Changes

| Component | Status | Action |
|---|---|---|
| EntityBase | present | keep, add `subject` canonical vocabulary in docs (Mathematics/Physics/Chemistry + future Biology) |
| KnowledgeComponent | present with `subject` attr | keep; canonical JSON now sets "Mathematics" explicitly |
| TaskModel/Method/Item | no subject attr | SAME subsystem; candidate: future patch adds `subject` too. NOT done this phase (no validation evidence). |
| Claim | uses subject_id/object_id to endpoints; no subject field | keep; cross-subject distinction derived from endpoint KCs |
| Cross-subject prerequisite | already supported | keep; validation test in this phase proves a KC(Math subject)→KC(Physics subject) PREREQUISITE validates |
| Store | in-memory | keep; queries by subject are handled by simple filters over `entities` |
| serialization | JSON via `dumps_store` | keep; `Subject` and `subject` propagate |
| export_view | neutral projection | keep; consumer resolves entity subjects as needed |
| validation | store validation + per-claim validator | keep; additively, we now have a test `test_cross_subject_prerequisite_validates` |
| documentation generation | generated by `tools/generate_math_cdg_docs.py` based on Mathematics pipeline | for Physics/Chemistry add a small subject param or separate generator templates (PROPOSED) |

## 3. Query patterns now supported
- All KCs in Mathematics: filter `entity_type==KnowledgeComponent && subject=="Mathematics"`
- All prerequisites of a Physics KC: filter Claims predicate==PREREQUISITE && object_id==<physics-kc>
- Cross-subject prerequisites of a Physics TM: for TMs whose KC is Physics,
  inspect their prerequisite edges whose subject KCs differ in `subject`.
- Shared prerequisites across subjects: group prerequisite sources by KC.id.

## 4. ID and naming conventions
- KC IDs remain opaque; subject NOT encoded in ID (per Sanity Check §8).
- Subject attribute is versioned; migration can re-home.
- Source IDs and evidence IDs unchanged.

## 5. Forward-compatibility checks
- No new database required: the typed store + validators scale; if a cross-
  subject CDG grows beyond in-memory comfort, that decision is deferred to
  a later phase with explicit requirement evidence.
- The canonical JSON stays single (`examples/math_cdg_v2.json`) and will
  gain `subject` on KCs and a top-level `Subject` entity record when the
  Physics/Chemistry construction phase begins.
